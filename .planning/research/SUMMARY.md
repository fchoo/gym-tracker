# Project Research Summary

**Project:** Gym Tracker  
**Domain:** Offline-first Android personal workout planner and logger  
**Researched:** 2026-08-16  
**Confidence:** HIGH overall; MEDIUM for device-dependent SQLite, notification, and Argon2id details until contract tests pass

## Executive Summary

Gym Tracker is a single-owner, Android-first training instrument: it combines reusable plans, a reviewed exercise library, one-tap guided workouts, recoverable rest timing, metric-aware history, and explainable progression without accounts, cloud sync, or opaque coaching. Experts should build this as a local-first modular monolith, not a backend-shaped mobile client: authoritative source facts live in one SQLite database; routes and screens call domain commands and queries; notifications, FTS, projections, recommendations, and TanStack Query state remain disposable or rebuildable derivatives. The approved product scope is already design- and engineering-reviewed, so roadmap creation must preserve the five reviewed delivery milestones rather than inventing new product areas.

The recommended implementation is Expo SDK 57 with React Native 0.86.2, strict TypeScript, Expo Router, `expo-sqlite`, local notifications, TanStack Query for disposable read models, Zod at persistence and import boundaries, and a narrow app-owned Argon2id Expo module for encrypted backups. The first milestone must prove the integrity kernel and a complete Full Body Foundation workout slice before catalog breadth or analytics. In particular, the reviewed intent is **repository-owned exclusive transaction ownership**, not direct reliance on Expo's `withExclusiveTransactionAsync()`: that helper opens a separate connection and begins before the callback, so connection-local `PRAGMA foreign_keys=ON` may be absent and cannot be enabled inside the active transaction. Use one preconfigured private writer, a FIFO write queue, explicit `BEGIN IMMEDIATE` / `COMMIT` / `ROLLBACK`, and a separate reader under WAL; verify foreign keys, rollback, concurrency, and commit-before-effects on actual Expo SQLite.

The dominant risks are false proof rather than missing features: migrations that cannot recover, restart tests mislabeled as Android process-death tests, notifications treated as timer truth, native/CNG breakage discovered at release, inaccessible screens retrofitted too late, and backup crypto or release promotion validated on bytes different from production. Mitigate them from Milestone 1 with clean CNG builds, real SQLite contract tests, durable pending effects, migration fixtures and failure injection, `killApp` lifecycle tests, explicit Android backup exclusions, adaptive/accessibility primitives, a native Argon2 feasibility spike, and digest-bound candidate promotion. Remaining gaps are implementation acceptance details—not invitations to expand scope—and must become explicit requirements or phase-plan fixtures before the affected feature is built.

## Key Findings

### Recommended Stack

Use the Expo SDK compatibility family as one locked native unit. Keep Expo-generated `~57.x` ranges for Expo-owned packages, exact-pin React and React Native as generated by SDK 57, exact-pin non-Expo application libraries, commit `package-lock.json`, and install with `npm ci`. Native or Expo dependency changes merge only after `expo install --check`, two clean prebuilds, real SQLite contracts, and Maestro smoke.

**Core technologies:**

- **Node.js `24.19.0` + npm `11.17.0`:** exact local and CI toolchain; declare `packageManager: "npm@11.17.0"`.
- **Expo SDK `~57.0.13`:** application platform and CNG owner; do not mix it with standalone React Native 0.87 or canary Expo releases.
- **React `19.2.3` + React Native `0.86.2`:** exact SDK 57 runtime pair.
- **TypeScript `~6.0.3`:** enable `strict`, `noUncheckedIndexedAccess`, and `exactOptionalPropertyTypes`.
- **Expo Router `~57.0.13`:** four-root-destination shell plus focused workout routes; application code imports navigation APIs from `expo-router`.
- **`expo-sqlite ~57.0.1`:** source facts, migrations, FTS5, pending effects, and projections; configure FTS, WAL, and foreign keys, but place write ownership behind the private serialized writer rather than exposing Expo transaction helpers.
- **`expo-notifications ~57.0.11`:** best-effort local rest projection; no push token or backend, and no exact-alarm permission by default.
- **`expo-haptics ~57.0.1`:** optional post-commit feedback only.
- **`expo-crypto ~57.0.1`:** AES-256-GCM for authenticated backup encryption.
- **`expo-file-system ~57.0.4` + `expo-sharing ~57.0.12`:** bounded local archive/CSV IO and explicit user sharing. Add Expo Document Picker through `expo install` for restore input as required by the architecture contract.
- **`@tanstack/react-query 5.101.4`:** disposable UI read cache with exact post-commit invalidation; never persist it or store workout truth in it.
- **`zod 4.4.3`:** versioned SQLite rows, effect payloads, content packs, notifications, backup envelopes, restore input, and CSV boundaries.
- **App-owned Expo Argon2id module + Bouncy Castle `bcprov-jdk18on 1.85.2`:** narrow password-KDF bridge; MEDIUM confidence until vectors, clean CNG builds, ABI/page-size compatibility, and minimum-device timing pass.
- **Jest `~29.7.0`, `jest-expo ~57.0.4`, RNTL `14.0.1`, Maestro `2.8.0`:** pure rules/components, real SQLite contracts in an installed development-test APK, and Android lifecycle/release E2E.

**Compatibility gates:**

- Pin CI to Temurin `17.0.20+8`; assert generated Gradle `9.3.1`, AGP `8.12.0`, Kotlin `2.1.20`, API `36`, minSdk `24`, Build Tools `36.0.0`, NDK `27.1.12297006`, New Architecture, and Hermes after clean prebuild.
- Keep generated `android/` ignored; commit app config, local Expo modules, deterministic config plugins, lockfile, scripts, and generated-contract assertions. Never hand-edit generated native files.
- Pin GitHub Actions to reviewed full SHAs. Build/sign candidates once, checksum them, approve the physical-device-tested digest, and publish those exact bytes without rebuilding.
- Expo Go and host mocks are not proof for SQLite connection semantics, notifications, custom crypto, migrations, process death, or release behavior.

### Expected Features

The feature set is approved. Requirements should distinguish expected category coverage from the stronger integrity and explainability that differentiate this product.

**Must have (table stakes):**

- Reusable user-owned plans, day templates, flexible schedules, five original starter plans, custom exercises, and a reviewed attributed 300+ exercise catalog.
- Fast offline workout logging with one active working set, one primary completion action, recommended/previous/default/manual values, separate warm-ups, editing, partial completion, and interruption continuity.
- Exercise-appropriate versioned metric profiles rather than assuming every observation is `weight × reps`.
- Timestamp-derived rest controls with pause/resume, adjustment, skip, next target, and correct in-app behavior when notifications are denied or late.
- Calendar, session detail, stable historical local dates, metric-aware exercise history, `Best` / `Average` / `Last`, and `N/N (100%)`-style completion.
- Searchable exercises with aliases, taxonomy filters, recent/favorite ordering, and custom content.
- Historical correction, reversible removal, deterministic dependent recalculation, encrypted backup/transactional restore, and versioned CSV export.
- System/Light/Dark, adaptive width classes, 200% text, keyboard/D-pad access, logical focus, reduced motion, non-color cues, and at least 48dp targets.
- A complete airplane-mode critical path with no account, backend, or runtime catalog dependency.

**Should have (approved differentiators):**

- One consistent `Next target` that shows evidence and rule version and never mutates a plan until explicit acceptance.
- Transaction-before-acknowledgement set completion: no visual success, advancement, rest, haptic, notification, or Undo state before the source/effect transaction commits.
- SQLite-authoritative rest recovery across process death, denied permission, late/stale notification delivery, Undo, foregrounding, and launch.
- One versioned metric contract from plan target through actuals, history, recommendations, backup, and CSV.
- Warm-up-safe and metric-aware analytics with no misleading aggregate kilogram volume or global fitness/readiness score.
- Auditable correction and reversible void/restore with targeted rebuilds equivalent to full rebuilds.
- Reviewed versioned content, immutable bundled templates, user-owned copies, and immutable session snapshots.
- Authenticated password-encrypted local data portability with bounded validation and no mutation on failure.
- Assistive interaction parity through the same command and transaction path, plus calm evidence-first language without guilt or medical claims.

**Defer or exclude (v2+ or deliberately absent):**

- Accounts, cloud sync, social/community features, sharing/leaderboards, and copied proprietary programs.
- Wear OS and Health Connect until the phone loop and local session model have real usage evidence.
- Generative coaching, camera form analysis, generic adaptive cardio coaching, medical/injury inference, nutrition, body measurements, photos, and recovery/readiness scores.
- Per-repetition or cluster-set timers, unlicensed exercise media, runtime scraping/remote catalogs, and marketing/store-listing art.
- Merge restore until stable identity and conflict rules receive a separate approved design; v1 uses previewed all-or-nothing replacement.

### Architecture Approach

Use a modular monolith with vertical `content`, `plans`, `workout`, `history`, `progression`, and `backup` domains; thin Expo adapters; one authoritative SQLite database; a private serialized writer; separate WAL readers; a narrow durable outbox; revisioned rebuildable projections; and a disposable TanStack Query UI cache. Dependencies point inward: routes import UI and domain public APIs, domains own rules and ports, adapters implement ports, and pure rules use only validated TypeScript values plus an explicit clock. Build folders incrementally with each vertical slice—do not scaffold future abstractions, add a sync engine, event-source the whole app, or introduce a generic event bus/ORM/DI framework.

**Major components:**

1. **Routes and UI/query layer** — four root destinations plus focused workout routes; forms and read models only, with no SQL or platform imports.
2. **Shared contracts** — stable IDs, metric/observation schemas, explicit clocks, typed errors, and redacted diagnostics.
3. **Content and plans** — immutable bundled packs, FTS/search, user-owned copies, schedules, targets, and monotonically increasing target revisions.
4. **Workout** — active session, immutable plan/exercise snapshots, set facts, rest revisions, completion, partial state, and Undo facts.
5. **History and progression** — corrections, void/restore facts, comparable exposures, deterministic recommendations, evidence, decisions, and optimistic acceptance.
6. **SQLite kernel** — connection ownership, ordered migrations, the serialized writer, repositories, pending effects, and projection stores.
7. **Effect runner and projections** — at-least-once idempotent notification reconciliation and subject-revision rebuilds that survive process death.
8. **Backup/platform adapters** — logical versioned export/import orchestration plus notification, haptic, file, crypto, and clock adapters.

**Transaction ownership contract:**

- The reviewed goal—repository-owned exclusive writes and commit-before-acknowledgement—stands, but direct `withExclusiveTransactionAsync()` does not satisfy it.
- Open one private writer at startup; apply `PRAGMA foreign_keys=ON` and bounded `busy_timeout` before transactions; configure WAL outside transactions; serialize all writes through a FIFO queue; use explicit `BEGIN IMMEDIATE`, `COMMIT`, and `ROLLBACK`.
- Keep only SQL and pure validation inside transactions. Write source facts and durable pending effects atomically, then run haptics, notifications, file IO, query invalidation, and UI work after commit.
- Contract-test the production wrapper on actual Expo SQLite for root/writer foreign-key state, invalid-FK rejection, rollback at every statement, concurrent unrelated queries, lock behavior, and absence of pre-commit effects. Repeat after every Expo SDK update and on the final release build.

**Data-flow patterns:**

- Start a planned session by snapshotting names, order, metric profile, units, targets, and rule versions.
- Commands return committed state plus exact query invalidation scopes; do not use a global database change listener or optimistic workout facts.
- Commit typed, revisioned pending effects with source changes; replay stale claims at launch/foreground and make every handler idempotent.
- Rebuild projections by affected subject revision; discard stale computations and require targeted/full rebuild equivalence.
- Reconcile Android notifications from persisted rest state and stable `sessionId`/`restRevision` payloads; a notification never becomes source truth.
- Use logical encrypted backups for users and SQLite hot backup only for internal pre-migration recovery.

### Critical Pitfalls

1. **Trusting Expo's exclusive helper as the integrity kernel** — its fresh connection can miss `foreign_keys`; use the configured private writer plus explicit serialized transactions and block feature work on real-device contracts.
2. **Shipping migrations that only work from an empty database** — keep a fixture for every released schema, update `user_version` in the same transaction, run both integrity and foreign-key checks, inject failures, retain bounded pre-migration recovery, and block the root shell on failure.
3. **Calling restart coverage process-death coverage** — persist at command boundaries, derive rest from timestamps, commit an outbox row with source facts, use Maestro `killApp` without clearing data, and test real reboot separately.
4. **Making notifications authoritative or promising exact reboot delivery** — SQLite remains truth; reconcile permission/channel/schedule state; ignore stale revisions; accept late delivery unless exact-alarm access is explicitly justified and tested.
5. **Deferring CNG/native proof until release** — clean-prebuild and install a development-test APK in Milestone 1, keep native configuration in deterministic plugins/local modules, verify generated manifests, and rerun native contracts after dependency changes.
6. **Freezing backup crypto before proving the native/resource envelope** — spike Argon2id early; authenticate metadata; bound KDF/file/decompression/row/string inputs; decrypt and validate before mutation; restore logical rows in one replacement transaction.
7. **Letting Android Auto Backup undermine manual encrypted backup and clean-install tests** — explicitly exclude SQLite and plaintext staging from cloud/device transfer through both API-family rules and verify the generated release manifest.
8. **Testing one APK and releasing another** — sign/build once, approve the artifact digest on a physical device, and promote the same APK/AAB bytes unchanged.
9. **Using screenshots or generic E2E as evidence they do not provide** — pair Jest/RNTL with real SQLite contracts, explicit permission states, native process-death/reboot tests, and manual assistive-technology verification.
10. **Retrofitting accessibility or universalizing progression rules** — establish adaptive semantic primitives in Milestone 1; implement versioned comparator/rule semantics per metric, exclude warm-ups and inappropriate partial exposures, and require explicit recommendation acceptance.

## Implications for Roadmap

The roadmap must preserve exactly the five reviewed delivery milestones. Cross-cutting infrastructure—CI, CNG, migrations, tests, accessibility primitives, backup/release seams, typed errors, and diagnostics—starts in Milestone 1 and evolves throughout; Milestone 5 closes and proves these concerns rather than introducing them.

### Phase 1: Trustworthy Workout Loop

**Rationale:** Every later feature depends on trustworthy source-fact writes, immutable session snapshots, lifecycle recovery, and one proven metric/recommendation path. Prove the architecture through a real vertical slice instead of building infrastructure or broad UI in isolation.

**Delivers:**

- Locked Expo/Android foundation, repository-root `DESIGN.md`, four-destination shell with intentional empty states, CI/test harness, clean CNG development-test APK, typed errors, and redacted diagnostics.
- Private configured SQLite writer, migrations and fixtures, durable pending-effects runner, exact invalidation, Android backup exclusions, and real native contract tests.
- Reviewed Full Body Foundation subset and immutable starter template activated as a user-owned copy.
- Today, active workout, warm-ups, transactional working sets, persisted rest, local notifications/haptics, process-death resume, partial finish, completion, basic session detail, `load_reps` history, and one versioned double-progression rule with evidence and acceptance.
- Early native Argon2 feasibility and release artifact/hash plumbing without implementing backup UI.

**Addresses:** Offline logging, starter-plan ownership, one-tap set completion, interruption recovery, basic history, `Next target`, transaction-before-acknowledgement, authoritative rest, and accessibility foundations.

**Avoids:** Expo transaction/foreign-key footgun, optimistic completion, non-recoverable migrations, fake process-death proof, notification authority, Expo Go/native drift, implicit Auto Backup, late adaptive primitives, and release-byte mismatch.

**Exit gate:** Actual Expo SQLite proves the production writer's foreign-key/isolation/rollback contract; working sets and pending effects commit before acknowledgement; `killApp` recovery and denied-notification behavior pass; clean CNG produces an installable APK; the airplane-mode Full Body Foundation loop is repeatedly usable; Argon2 feasibility and artifact retention/hash paths are proven.

### Phase 2: Owned Library and Planning

**Rationale:** Stable content identity, user-owned plans, snapshots, schedules, FTS, and explicit metric profiles must exist before broad history and progression can be trusted.

**Delivers:**

- Frozen reviewed 300+ content pack, attribution/source revision, aliases, taxonomy, unavailable-source behavior, FTS5 search/filter/paging, and repair/rebuild tooling.
- Custom exercises; complete plan/day editor; rename, duplicate, reorder, archive, weekday/rotation/override/rest-day/Train-anyway behavior; and all five original starter plans.
- Remaining resistance/timed metric profiles needed by starter plans, each with explicit comparator, aggregate, tie, precision, and version fixtures.
- Content and migration fixtures that preserve custom rows, copied plans, and historical snapshots through upgrades.

**Addresses:** Reusable plans, flexible scheduling, searchable library, custom exercises, metric variety, reviewed content ownership, and complete starter-plan usability.

**Avoids:** Bundled/user-owned generic upserts, FTS as a second truth store or raw query language, generic comparator direction, schedule ambiguity, catalog drift, and mutable historical display.

**Exit gate:** Custom plans run without mutating bundled templates; content upgrades preserve user-owned data and snapshots; FTS/relational stable IDs remain in parity after every write path; every starter plan references reviewed exercises and explicit progression policies.

### Phase 3: Calendar and History Integrity

**Rationale:** Corrections and reversible removal change effective old history. Their source facts, subject-revision fan-out, invalidation, and deterministic rebuild behavior must stabilize before period analytics and full recommendation breadth.

**Delivers:**

- Calendar visit states, stable local training dates, full session detail, metric-aware exercise history/trends, and `Best` / `Average` / `Last`.
- Exhaustive correction field/action rules, correction audit ledger, reversible void/restore, affected-subject revisions, durable invalidation/rebuild effects, and projection diagnostics.
- Recalculation of records, comparable history, summaries, and pending recommendations after history changes.

**Addresses:** Calendar/history table stakes, historical correction/removal, auditable correction, metric-aware evidence, and rebuildable derivatives.

**Avoids:** Append-only watermarks for mutable history, stale recommendations/projections, hard deletes, silent historical rewrites, and timezone date drift.

**Exit gate:** Corrections, voids, and restores produce targeted rebuilds identical to full rebuilds; dependent pending recommendations are invalidated before acknowledgement; timezone changes do not move historical visits.

### Phase 4: Overall Progress and Complete Progression

**Rationale:** Period summaries and recommendations are credible only after comparable history, correction semantics, projections, and all required metric comparators are stable.

**Delivers:**

- Overall Progress for 4 weeks, 12 weeks, and All time; scheduled-opportunity consistency; needs-attention, recent-improvement, record, and searchable exercise views.
- Text summaries and accessible tables that share source queries with charts.
- Remaining versioned profile-specific recommendation rules, plan-authored cardio/interval policies, effort input, stored evidence, and accept/reject/invalidate/supersede lifecycle with optimistic concurrency.

**Addresses:** Overall progress, complete explainable progression, evidence-first feedback, accessible analytics, and all approved recommendation states.

**Avoids:** Aggregate kilogram volume, global readiness/fitness scores, zero-valued sparse analytics, generic cardio coaching, warm-up pollution, medical claims, stale recommendation overwrite, and inaccessible chart-only meaning.

**Exit gate:** Every summary drills into source sessions/exercises; every recommendation is reproducible from stored evidence and a versioned rule; no pending, stale, or unaccepted recommendation mutates a plan; sparse history yields explicit baseline/Hold behavior; every chart has equivalent text/table output.

### Phase 5: Recovery, Distribution, and Release

**Rationale:** The logical user-backup schema should follow stable source-fact ownership, but security feasibility, native/CNG compatibility, accessibility architecture, and release artifact identity were already proven earlier. This phase completes user-facing recovery and closes release evidence.

**Delivers:**

- Versioned logical backup, Argon2id-derived AES-256-GCM envelope, bounded file/resource validation, restore preview, one-transaction user-owned replacement, bundled-reference reconciliation, full projection/FTS rebuild, and versioned CSV.
- Final System/Light/Dark, compact/medium/expanded, rotation, 200% text, keyboard/D-pad, logical-focus, reduced-motion, and non-color verification.
- Signed APK/AAB candidates, checksums, protected physical-device digest approval, unchanged GitHub Release promotion, migration suite across retained versions, and post-implementation design review.

**Addresses:** Safe local ownership, backup/restore/export table stakes, release distribution, complete adaptive/accessibility verification, and production-readiness evidence.

**Avoids:** Weak or unbounded crypto, parse-before-authenticate, raw database restore, partial mutation, Auto Backup contamination, plaintext residue, emulator-only proof, release rebuild after approval, and publishing inaccessible or visually unverified bytes.

**Exit gate:** Known-answer and frozen archive fixtures pass; wrong-password/tamper/unsupported/oversized/failed inserts mutate nothing; restore succeeds into an independently clean install; minimum-device resource budgets pass; release assistive/lifecycle/device matrix passes; the public APK digest exactly matches the physically approved candidate.

### Phase Ordering Rationale

- Milestone 1 establishes the write, migration, effect, lifecycle, native-build, accessibility, and release-evidence contracts that every later domain uses.
- Milestone 2 stabilizes content identity, ownership, schedules, snapshots, search, and metric semantics before broad historical derivation.
- Milestone 3 makes historical mutation safe and deterministic before Milestone 4 builds analytics and recommendation breadth on top.
- Milestone 4 consumes current comparable evidence and revisioned projections rather than inventing independent UI calculations.
- Milestone 5 freezes portable backup/CSV contracts only after source-fact schemas stabilize, while completing—not beginning—native security, adaptive, accessibility, and distribution proof.
- Every milestone leaves a buildable repository and a usable included flow; no milestone may bypass its data-contract dependencies.
