## Moderate risks

| Risk | Required mitigation |
|---|---|
| Switching plans hides past missed work | Remove current-lifecycle filtering from historical opportunities (`historyRepository.ts:788`); apply activation only to future previews. |
| Calendar turns two sports into one date status | Return stable event identities and separate source/status fields. Never dedupe by local date, label or sport alone. |
| Same-date plan edit redirects an already presented import match | Derived opportunity ID currently includes schedule/date/source but not version (`scheduleRepository.ts:1527`). Confirm against schedule/version/day revisions; materialize the intended opportunity in the match transaction. |
| Retrospective matches change missed counts without audit | Append match/unmatch facts. Rebuild effective completion and consistency from documented rules; preserve original missed fact, with correction visible. |
| Timezone change shifts the other plan or historical dates | Prompt/acknowledge per schedule; use stored schedule timezone and historical creation context. Never convert date-only opportunities through UTC date truncation. |
| New columns silently omitted by legacy inserts | All newly created Running roots/schedules explicitly provide kind. Legacy default is compatibility only. Add insert-path coverage for create, copy, duplicate, activate, restore and merge. |
| Legacy recovery cannot prove a schedule version | Preserve session, rest and set state; withhold automatic schedule effects rather than using current active pair. Supply an actionable resolution. |
| Immature calendar query scales with all history | Existing month query scans all sessions then runs per-session counts. New range query must handle overlay effective dates and batch counts; avoid dropping moved-in/out corrected sessions. |
| Raw Running samples exhaust existing backup bounds | Follow Garmin ADR for bounded sample chunks/payload limits. Test actual encoded snapshot size and counts before authorizing source-table layout. |
| Duplicating Running plan accidentally shares mutable payloads | Copy profile and day revisions into fresh owned identities; schedule inactive; original and duplicate evolve independently. |
| Hiding cadence controls leaves invisible cues running or destroys recovery | Preserve old snapshots/state as dormant legacy data; gate all retired playback/reconciliation, including queued callbacks. Resume sets/pointers/between-set rest. New snapshots resolve timing off. If isolation cannot be proved, block cutover and use a reviewed compatibility path. |

## Preflight and migration transaction

1. Quiesce repositories before schema work. Retain the source database; do not inspect or mutate a live phone DB during planning.
2. `createMigrationRunner` obtains and validates a recovery copy for the constraint-changing migration. Existing checks include `user_version`, `foreign_key_check`, and `integrity_check` through `RecoveryBackupPort`.
3. Validate the old model: at most one active plan/schedule, pair identity agreement, valid parent ownership, no duplicate schedule per plan, at most one in-progress session. Do not silently repair unsupported/corrupt states.
4. Add checked `plan_kind` columns with `strength` defaults. Create the new per-kind indexes and type/identity guards. Drop global plan/schedule indexes only after replacements exist in the same transaction.
5. Create typed Running/provenance/match source tables and derived relation tables in dependency order. Install no-delete/immutability/identity guards and automatic-backup generation triggers after each authoritative table exists.
6. Backfill only facts that are deterministic. Existing plan kind defaults do not change IDs or revision histories. Derive links for already-consumed Strength opportunities from their existing session FK if needed. For an interrupted legacy session, prove a unique plan-owned schedule/version before attaching a link; leave uncertain schedule attribution unresolved while preserving recovery.
7. Verify schema shape, exact index predicates, pair coverage, typed readiness, identity uniqueness, FK integrity and unchanged canonical source content. Schedule opportunities/overrides and rotation pointers remain unchanged.
8. Commit `user_version` with the transaction. A failure at any point rolls back both schema and source mutations. An uncertain commit is resolved by reopening and reading durable schema/receipts, not blindly rerunning commands.

**After a migration error:** use a fresh runner on restart; the current runner intentionally raises `migration_retry_requires_restart` on reuse. Show the existing migration/recovery failure surface until trusted reads succeed. Do not delete the source or recovery database automatically.

**Rollback:** before any post-upgrade owner mutation, restoring the validated pre-upgrade copy can recover v1.1. After new Running data is committed, rollback to v1.1 loses unsupported data unless preserved separately; use a forward repair/export recovery path. Installing an old binary is not a supported schema downgrade.

## Failure reporting contract

Use existing typed storage/domain error conventions. Specific new codes should distinguish duplicate active sport, pair mismatch, stale selection, invalid Running graph, unsupported backup schema, ambiguous legacy schedule attribution, and match conflict. Diagnostics contain codes, versions, aggregate counts and hashes only. Do not log workout payloads, imported route samples, file paths containing personal data or authentication material.

No catch block may silently fall back to the first active plan. No failed match may mark a schedule complete. No failed migration may expose an apparently usable Workout root. Keep new preflight errors actionable and preserve the owner's existing recovery copy.
