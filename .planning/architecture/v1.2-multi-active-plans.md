# ADR proposal: concurrent Strength and Running plans

**Status:** Proposed for owner review; no implementation approval implied.  
**Date:** 2026-10-06  
**Baseline:** `703b9d21a900dcadbcd4138c3691256174667bf1`, SQLite schema 27.  
**Authority:** `.planning/v1.2-OWNER-BRIEF.md`, then prototype `approved.json` revision 18. The owner brief approves the prototype as the planning target; its stale `awaiting_owner_review` metadata does not block planning. The separate domain decisions below remain proposals.

## Decision being proposed

Support **zero or one active Strength plan and zero or one active Running plan concurrently**, with independently versioned schedules. Keep exactly one in-progress Strength workout globally. Garmin remains the Running recorder; a Running plan never starts an in-app tracking session. The owner brief requires concurrent plans but does not explicitly settle multiple plans within one sport. **The per-sport limit is proposed and awaits the owner's cardinality answer.** If multiple same-sport plans are required, remove the per-sport uniqueness proposal and use explicit ordered plan selection; retain every identity, scheduling, history, and import boundary below.

Keep the existing SQLite kernel, owned plan identities, schedule engine, and backup system. Add typed Running authoring and imported activity facts beside Strength sets. Do not make a second scheduling implementation or synthesize Strength workouts from running imports.

## Exact singleton assumptions to remove

1. `starterPlanRepository.ts:259` rejects more than one active plan or schedule, and `expectedActiveRevisionMatches` accepts only a scalar schedule revision. Its `deactivatePrevious` path changes one global previous pair.
2. `scheduleRepository.ts:824` rejects more than one pair. Activation replaces the global pair at approximately lines 1000–1080. Scope by target `plan_kind`; reject duplicate pairs within that kind.
3. `scheduleRuntime.tsx:495` rejects more than one active schedule. `actOnToday`, `setDateOverride`, `consumeDateOverride`, `chooseTimeZone`, `recordTrainAnyway`, and `markWeekdayMissed` find a singleton implicitly. Each must receive explicit plan/schedule identity and expected revisions.
4. `scheduleRuntime.tsx:922` completes a session using the **currently** active schedule. Completion/retry must resolve the session's captured schedule, even if a later activation changes the current selection.
5. `plansWorkoutRepository.ts:1374` and `:1540` select an arbitrary copied active plan with `LIMIT 1`; `getActivation()` also returns hardcoded Full Body Foundation source metadata. `existingActivation()` at `:485` is template-scoped but still legacy. Production Today must stop relying on these legacy selectors; any retained compatibility method must explicitly mean Strength and validate ambiguity.
6. `workoutAppRuntime.tsx:2090` combines legacy and owned singleton Today reads. `startPlanDay(dayId, mode)` at `:2474` discovers the plan independently of the selected day. Change to a validated selection containing `planId`, `planDayId`, `scheduleId`, version/opportunity identity and revisions.
7. `workoutAppRuntime.tsx:1913` rejects two schedules in starter preview. `:2000` and `:2030` join any active schedule into a template-update preview; with two plans these become multi-row joins. Join the target sport explicitly, not the first returned row.
8. `restoreCommands.ts:224` combines one-active-plan and one-in-progress-session checks. Split them and retain the latter globally.
9. `mergePlan.ts:1107` and `:1157` suppress imported activation when **any** local active plan/schedule exists. Replace with an explicit paired, per-sport activation resolution pass over the entire projected merge result.
10. `historyRepository.ts:783` filters recorded missed opportunities by current schedule lifecycle and emits only date/status sets. This loses event identity and can hide past missed facts after switching plans. Preserve historical opportunities independent of current activation and build future previews only from applicable active schedules.

## Proposed schema and authority

Names in this section are proposed implementation names, not existing tables.

| Entity | Authority and invariant |
|---|---|
| `plans.plan_kind` | Immutable `strength` or `running`; canonical plan type. Existing plans backfill to `strength`, without reclassifying old mixed or timed exercise history. |
| `owned_plan_schedules.plan_kind` | Validated copy of parent type, needed for a local partial unique index. Never editable independently. |
| `running_plan_profiles` | One row per Running plan: goal/benchmark configuration, optional target date and weekly distance, draft/ready/archived lifecycle, revision. No invented target values. |
| `running_plan_sessions` / `running_plan_session_revisions` | Stable session identity plus immutable structured revisions. Recovery, Long run, Progression, Tempo, Intervals, Hills, and Fartlek use a discriminated union. Ordered phases carry warm-up/work/recovery/repeat/cool-down and advisory pace/HR-zone/RPE. A plan may hold zero, one, or several ordered sessions on the same weekday. |
| `running_schedule_session_bindings` | Binds a schedule version, stable Running session and exact immutable revision to `weekday` plus `slot_ordinal`. `UNIQUE(schedule_version_id, weekday, slot_ordinal)` preserves deterministic same-day order without weakening Strength's existing one-binding-per-weekday invariant. |
| `workout_session_schedule_links` | Immutable provenance for newly started Strength sessions: session, plan/day, schedule/version, local date/timezone, selected opportunity if consumed, start mode and command identity. Empty workouts have no schedule link; alternate work never consumes a scheduled opportunity by inference. |
| `imported_activities` and companion tables | Immutable imported facts owned by the Garmin/import ADR. No dependence on an active plan, and no insert into `workout_sessions`. |
| `running_activity_match_events` | Authoritative owner-confirmed match/unmatch events with stable portable identity, request hash, expected link revision, imported activity identity, opportunity/schedule version/stable session slot/session revision. Same request/hash replays; changed payload under same request conflicts. |
| `running_opportunity_completions` | Rebuildable current relation derived from match events. Unique current activity and opportunity; retains last relation revision so a stale confirmation cannot overwrite a newer match. |

Reuse the schedule-version, effective-date, timezone, override, opportunity and receipt engine for both sports. Preserve Strength `plan_days` and its existing schedule-binding uniqueness unchanged. Running sessions use their own ordered binding child because a weekly program may intentionally contain multiple sessions on one weekday. Keep `owned_plan_aggregate_states` and its exact missing-target contract for Strength. Running readiness lives in `running_plan_profiles` and a typed readiness validator; the common activation command delegates to the correct validator. Do not label a complete Running program invalid because it lacks `owned_plan_working_set_targets`. Generic library/backup/ownership checks must account for both aggregate kinds. Extend permanent-delete guards to Running roots, sessions, revisions, bindings, and match facts.

**Proposed scope choice:** Running uses **Weekday** scheduling because the approved builder is a structured weekly program. Strength keeps Weekday and Rotation. Running supports multiple stable session slots on the same weekday, ordered by explicit ordinal; reorder changes a future schedule version and never historical occurrences. General Running rotation and partial multi-file fulfillment remain separate owner decisions. Strength's existing `UNIQUE(schedule_version_id, week_index, weekday)` stays intact, while the Running binding table adds the slot ordinal needed by the approved builder.

## SQL migration strategy

Reserve `0028_multi_active_plan_kinds.ts` as the next migration **only if schema 27 remains current**. Register the actual next version at implementation. Use `kind: 'destructive'` for the constraint replacement so `createMigrationRunner` requires a validated recovery backup, despite retaining every source row. All statements, validation and `PRAGMA user_version` commit in one kernel transaction.

Illustrative migration SQL, subject to implementation verification:

```sql
ALTER TABLE plans ADD COLUMN plan_kind TEXT NOT NULL DEFAULT 'strength'
  CHECK(plan_kind IN ('strength', 'running'));
ALTER TABLE owned_plan_schedules
  ADD COLUMN plan_kind TEXT NOT NULL DEFAULT 'strength'
  CHECK(plan_kind IN ('strength', 'running'));

-- Validate legacy pair cardinality, plan/schedule agreement, and readiness first.
-- Abort with a diagnostic code on corrupt input; never select an arbitrary winner.
CREATE UNIQUE INDEX one_active_plan_per_kind ON plans(plan_kind)
  WHERE is_active = 1;
CREATE UNIQUE INDEX one_active_schedule_per_kind
  ON owned_plan_schedules(plan_kind) WHERE lifecycle = 'active';

CREATE TRIGGER plans_kind_immutable
BEFORE UPDATE OF plan_kind ON plans
WHEN NEW.plan_kind <> OLD.plan_kind
BEGIN SELECT RAISE(ABORT, 'plan_kind_immutable'); END;

CREATE TRIGGER owned_schedule_kind_insert
BEFORE INSERT ON owned_plan_schedules
WHEN NOT EXISTS (
  SELECT 1 FROM plans
  WHERE id = NEW.plan_id AND plan_kind = NEW.plan_kind
    AND origin IN ('custom', 'copied')
)
BEGIN SELECT RAISE(ABORT, 'schedule_plan_kind_mismatch'); END;

CREATE TRIGGER owned_schedule_kind_update
BEFORE UPDATE OF plan_id, plan_kind ON owned_plan_schedules
WHEN NEW.plan_id <> OLD.plan_id OR NEW.plan_kind <> OLD.plan_kind
BEGIN SELECT RAISE(ABORT, 'schedule_identity_immutable'); END;

DROP INDEX one_active_owned_schedule;
DROP INDEX one_active_owned_plan;
```

Create new indexes before dropping old ones within the same transaction. SQLite partial-index predicates cannot reference another table, so a predicate joining `plans.plan_kind` is invalid. The schedule copy plus immutable identity/type guards is an explicit small duplication, not a second editable source. New Running inserts must supply `plan_kind='running'`; the default exists only for legacy compatibility. Verify index SQL via `sqlite_master`/`PRAGMA index_list`, not only index names.

The two active flags remain paired repository-owned state. Indexes prevent more than one per kind but do **not** guarantee that active plan A and active schedule B refer to the same plan. Run a shared `assertActivePlanPairs(transaction)` before command acknowledgment and during migration/restore/merge verification. It must check one-to-one pair agreement, matching kinds, owned origin, ready/not archived state, and absence of orphan active flags. Avoid immediate cross-table activation triggers that reject valid transient steps inside the paired transaction.

Do not rebuild `workout_sessions`, `session_sets`, or existing opportunities just to add Running. The existing opportunities table requires a Strength `session_id` for `outcome='completed'`; imported fulfillment is a separate match ledger. The shared effective-opportunity resolver overlays Running fulfillment. All Running skip/missed/override/activation validation must consult that same resolver under the writer transaction, so a matched run cannot later be silently marked missed.

## Activation and authoring flow

```text
Create plan(kind) -> save inactive typed graph -> preview activation
  -> capture target revision + expected active pair FOR THAT KIND
  -> owner confirms
  -> exclusive transaction:
       replay request receipt if already committed
       validate target kind/readiness and current pair/revisions
       deactivate old pair of this kind only
       activate selected plan and its own schedule
       append event/receipt + assert paired invariants
     COMMIT -> invalidate typed Today/Library/Calendar/backup generation
```

An activation preview identifies both old and new plan names and sport. Strength activation preserves the Running schedule's revision, pointer, overrides and opportunities, and vice versa. Use full pair expectations, not a revision number that might belong to either sport. Preserve the existing active-workout protection initially; allowing unrelated Running activation during a Strength workout is **proposed, not required**, and may be enabled only after showing it cannot affect captured session provenance. Creation, duplication, starter copy and imports stay inactive unless a separate activation action is explicitly confirmed.

Running edits append day revisions and prospectively bind new schedule versions. Validate structured payload sizes, integer units and type-specific required fields in pure domain functions. An accepted Running target remains advisory; imports do not automatically change it. Changing a plan from Strength to Running is not supported as an in-place edit; create a new plan and preserve the old identity/history.

## Today and same-day collision policy

Read a coherent SQLite snapshot into `TrainingTodaySnapshot` containing `recovery`, `strength`, `running` and per-plan schedule context. New proposed paths are `src/domains/scheduling/activePlanSelection.ts` for pure selection and `src/platform/sqlite/repositories/trainingCalendarRepository.ts` for unified date-range events. Keep SQL out of screens.

1. An in-progress Strength session remains the primary action; saved partial recovery keeps the existing priority. Recovery is resolved by session identity, never by whichever plan happens to be selected now.
2. The Workout root presents the Strength workout as its primary workout content and Running as the contextual plan/import entry shown in the prototype. A Running-only day exposes its plan and import context; never invent a Start Run action.
3. A same-date Strength and Running opportunity produces two distinct events. Completing one does not complete, skip, move or suppress the other. They have no time-of-day conflict unless time scheduling is separately introduced.
4. Stable display order is proposed as date, known start time, sport order Strength/Running, stable event identity. A display preference may change ordering but never activation or schedule pointer.
5. Rest/skip/missed state is per plan. No global rest-day result may hide a pending opportunity in the other sport. Date overrides, timezone prompts and their acknowledgments are per schedule; each uses the schedule's stored timezone.

These defaults implement the approved two-sport composition. If rendered prototype interactions require another primary selection policy, record the exact mismatch and obtain a decision rather than silently changing presentation.

## Calendar and history preservation

Return typed events with stable ID, sport, source identity, local date/timezone, title, status, plan/day-or-running-session/schedule/version/slot context, optional workout/import identity, and detail destination. Strength history uses effective snapshots and existing audit overlays. Running history uses imported facts and match events. Future planned events are a bounded replay of active schedule versions; previews do not create source opportunities or mutate rotation pointers. Several planned Running session slots on one date remain several independently addressable events.

Keep the existing local date of historical facts; do not regroup old events because the device timezone changed. Aggregate by date with separate events rather than only a set of status flags. A matched Running activity fulfills its single planned opportunity in the agenda; an unmatched import remains a standalone event. Do not deduplicate two unrelated events merely because their title/date matches. Removing a current plan from activation hides its future preview only; past completed, partial, missed and explicitly matched records stay visible.

Preserve every Strength session/metric snapshot, correction, undo fact, rest state, source target link, portable identity and stored advanced-timing configuration. The owner requires no cadence or nested timing UI. Removing that feature does not authorize deletion of its historical configuration or modification of recorded set/rest facts. The compatibility policy below separates retained facts from retired advisory playback.

### Legacy cadence/cluster compatibility proposal

Shipped Phase 10 explicitly treats cadence and cluster gaps as advisory, separate from between-set rest (`10-CONTEXT.md:9`, `:41`). The live schema confirms separate `session_advanced_timing_states` and `session_rest_states`. Therefore a forced finish/discard of an interrupted workout is not inherently necessary to retire the feature.

**Recommend a v1.2 runtime capability policy, not destructive data cleanup:**

1. Retain schema-21/27 columns, config JSON, state rows, target ownership checks and backup parsing. Do not rewrite existing `session_sets.advanced_timing_resolved_json`, plan defaults, committed set values or historical state merely to make them appear off.
2. Remove cadence/cluster authoring from plan, exercise and set controls, including `AdvancedTimingConfigSheet` and `AdvancedTimingIndicator`. Keep the prototype's flat between-set rest controls with explicit `sec`. Metric types such as timed hold remain ordinary exercise observations; they are not cadence.
3. Disable all advisory cadence/cluster command and playback entry points for v1.2, including foreground reconciliation and already queued callbacks. Relevant seams are `workoutAppRuntime.tsx:2547` (context), `:3196` (active timing reconciliation), `:3240` (command wrapper), `:3280` onward (configure/start/gap/pause/resume/reconcile), and the corresponding ActiveWorkout screen effects. Gating only visible controls is insufficient: hidden foreground reconciliation can still emit cues.
4. New session/set snapshot construction resolves advanced timing to the existing off config while preserving other source targets. Keep old plan timing defaults as dormant legacy data; the new runtime does not inherit them. New user edits write only supported rest fields. Fresh duplicated plans may omit retired timing defaults; existing identities and history remain unchanged.
5. An interrupted or saved-partial legacy session resumes with the same committed sets, draft values, active pointer, schedule provenance, and between-set rest. Its old cadence/cluster metadata remains readable for portability but is not played or advanced. Give a concise compatibility notice when relevant: repetition/cluster cues are no longer available; saved sets and between-set rest are preserved. Do not add a nested timing route or a completion gate.
6. Apply the same capability boundary after manual restore, merge and automatic replacement recovery; no old archive may re-enable retired playback. Keep device/system sound and haptics for supported between-set rest unchanged.

The existing `stopAdvancedTiming` transition (`advancedTimingRepository.ts:969`) is available if a later approved policy requires terminalizing mutable advisory state, but it is **not** permission to rewrite immutable configuration snapshots during migration. Retaining old runtime rows dormant is the smallest data-preserving default.

Before launch, prove zero cadence/cluster cues across foreground, queued callback, relaunch and restore cases while between-set rest still recovers correctly. If that cannot be demonstrated, block cutover and retain the old recovery path until the session is completed/parked under an explicitly reviewed compatibility design. Do not silently ship a UI-only removal. This proposal implements the owner's feature retirement without requiring a new preference question; any unavoidable extra recovery presentation must be registered as a deviation for review.

## Import matching and fulfillment

```text
Import file/API -> validate/dedupe -> commit independent imported activity
  -> optional candidate list (no schedule write)
  -> owner confirms ONE activity + ONE planned opportunity
  -> exclusive transaction:
       revalidate import, plan/session revision, schedule/version/slot, date and link revision
       materialize deterministic pending opportunity if still only a preview
       append match event + rebuild affected current completion relation
       preserve original imported facts and planned targets
     COMMIT -> Calendar/Progress rebuild + backup dirty generation
```

Use a local FK to `imported_activities.id`; portable serialization/remapping resolves the owner namespace plus portable ID, not a date or title. Capture source hash/revision in the confirmation. Running opportunity identity includes the stable schedule-session slot, so two sessions on one date cannot collapse to a date-only candidate. Existing derived opportunity IDs use schedule/date/source, not version; validate the schedule version and exact session revision before materializing so stale confirmation cannot attach to a newly edited session. Keep the confirmation bound to the selected materialized opportunity afterward.

An unmatch appends an event and rebuilds the relation; it does not delete the import or rewrite Strength completion. Proposed one-to-one match uniqueness prevents an import counting twice. A late import can be matched to an inactive plan's historical opportunity after explicit review; it must not reactivate the plan. Same-day/time proximity can rank candidates but cannot confirm them. Running rotation and cumulative multiple-activity fulfillment remain deferred pending owner need.

## Backup, merge, restore and recovery

- Extend the same logical GTBK/Drive graph; do not fork a separate Running backup product. Preserve manual encryption and current Drive quarantine/writer fencing. Transport credentials remain outside the logical workout archive.
- Add every authoritative Running/import/match/provenance table to `backupContracts.ts`, `logicalBackupRepository.ts` ownership filters, `restoreCommands.ts` reference/type/default rules, `mergePlan.ts` conflict classes and ID maps, and `logicalMergeRepository.ts` closure validation. Rebuildable completion/calendar relations are excluded and reconstructed before restore becomes ready.
- Preserve supported older schema restore paths with versioned table sets and default `strength` columns. The exact-key parser rejects extra/missing fields, so adding SQL defaults alone is insufficient. Old in-progress records keep their old snapshots; exact Strength schedule provenance may be backfilled only from uniquely provable schedule/version facts. Ambiguity preserves the session and withholds automatic schedule consumption for review.
- **Proposed merge policy:** keep local active pair per sport; retain imported distinct plans as inactive when that sport is occupied. If a sport is empty, preserve an archive active pair only when unambiguous and shown in the merge preview. Creation/file import never activates; recovery of previously active backup state is a separate operation. Resolve all candidates together rather than independently per imported aggregate, which could otherwise select two winners.
- Same portable plan with conflicting kind is a validation conflict, never an implicit conversion. Distinct plans remain distinct. Imported activity IDs/hashes are deduplication evidence, not schedule match authority. Conflicting current match relations require an explicit preview choice; never silently choose by import order.
- Restore-clean preserves both valid archive pairs after validation. A new archive with duplicate active kinds, inconsistent pair flags, invalid match FKs or multiple in-progress Strength sessions fails before mutation. A legacy archive retains its original single pair, defaulted to Strength.
- `migrationRunner.ts` already verifies inside the transaction and commits `user_version` with it. Reopen with a new runner after a failed attempt; an in-memory runner is deliberately single-use. Retain the validated pre-upgrade recovery artifact until the new release is accepted. Do not downgrade schema by installing the old app over the upgraded database.
- `0023_automatic_drive_backup.ts` imports the live `LOGICAL_BACKUP_TABLES`; first make its table list version-specific so fresh installs do not create triggers on future tables. New migrations create new generation triggers after their tables, and restore/merge must reinstall them correctly. Old migration SQL behavior must remain equivalent.

No new production package or build is authorized by this proposal.

## Review findings: quality, tests, performance

**Code quality:** centralize active-pair validation and typed readiness; eliminate duplicated singleton fallback queries. Make command identity explicit in arguments. Keep Strength and Running validation separate where their semantics differ, sharing scheduling/date/revision primitives.

**Tests:** migration failure injection, old/new backup matrices, paired activation, cross-sport independence, stale selection, process death after commit, import matching/remapping, and deterministic projection rebuild are mandatory. Detailed cases live in `v1.2-migration-risks.md`.

```text
Pure kind/readiness/selection + schedule transitions
                 |
Real SQLite fresh/legacy migrations + constraint rejection
                 |
Activation -> start snapshot -> completion/replay
   |                              |
Other sport unchanged       match/unmatch/import replay
                 \          /
             backup -> restore / merge -> rebuild parity
                             |
             Android crash/relaunch + offline + UI parity
```

**Performance:** query active pairs once, bounded by two under the proposed limit. Load the visible calendar range plus adjacent weeks; batch session summaries and imported summaries. Existing history month loading scans all source sessions and counts each session separately (`historyRepository.ts:762`, `:797`); reusing it unchanged will multiply work. Inspect query plans and bounded fixtures during implementation. The 150 ms set-commit budget remains unchanged; import parsing and calendar rebuild run outside the workout command critical path.

## Not in scope

- In-app outdoor/treadmill recording, GPS permissions, or Running foreground-service lifecycle: explicitly excluded by owner.
- Multiple users, concurrent multi-device sync, hosted workout storage: unchanged scope boundary.
- Inferring historical sport from timed metric profiles, automatic schedule matching, automatic target acceptance: violates identity/evidence contracts.
- Retrofitting unlimited active plans, Running rotation, or cumulative multi-activity fulfillment: unresolved or deferred, not silently included. Ordered same-day Running session slots are included because the approved builder permits them.
- Deleting legacy advanced-timing source facts because the new UI hides controls: not authorized.
