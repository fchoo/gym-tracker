## Decision

Create one local import pipeline for owner-selected original FIT files and future approved Garmin Activity API deliveries. Preserve imported running activities as their own immutable source aggregates. Do not synthesize strength `workout_sessions` or completed sets. Display imports in the existing Workout/Calendar/Progress navigation. Matching an import to a scheduled Running opportunity is a separate, explicitly confirmed, revision-checked transaction.

Implement the manual path independently of developer approval. Keep official connectivity unavailable until the activation checklist in this ADR is satisfied. Garmin's public FAQ says business use only; its public PKCE PDF requires `client_secret` at code exchange. The default future official topology therefore includes a confidential broker, whose hosting and authentication require review. No Garmin credentials are available or presumed in this research. No endpoint, scope, quota, callback signature, or approval outcome is invented. [G1–G3]

Use existing SQLite/portability/file/crypto conventions. Reuse installed SVG for the approved static route outline and charts, and installed Gesture Handler/Reanimated for native presentation. The architecture does not add live recording, watch apps, direct watch access, Training API workout push, account scraping, or a fifth root tab.

## Source model and identities

Final migration numbers are allocated by the domain-foundation phase after checking the current migration registry. Keep source ownership explicit. All portable identities use the existing owner namespace plus portable ID; a bare imported integer ID or provider activity ID is not a cross-install identity.

`imported_activity_payloads` means observed normalized payload revisions, not a promise to retain original files. Recommended retention is temporary raw FIT until successful normalization/commit, followed by cleanup. Preserve all **supported** source channels losslessly, the original content hash, parser version, and a capability/missing-fields summary. Unknown developer fields and unsupported source messages are not fabricated. Optional permanent original retention is an unresolved privacy/capacity decision, not a hidden fallback.

### Idempotency rule

Use **two independent indexes**, not one composite key that treats each changed hash as another completed activity:

1. Verified external reference: `(owner, provider, providerSubject, externalActivityId)` when available.
2. Payload fingerprint: `(owner, sha256(exact FIT bytes))`, associated with the existing source activity/payload.

Hash the unmodified FIT bytes consumed by the decoder, before numeric normalization. A normalized semantic fingerprint can help suggest a possible duplicate, but it must never automatically merge two runs. Identical timestamps/distance can occur in distinct activities. A file's name, `file_id` metadata, device serial, and creation time are not assumed to be a Garmin Connect cloud activity ID. Manual import therefore has a nullable external reference. [G4, F1–F2]

| Observed input | Required result |
|---|---|
| Same external ID and same FIT hash | Existing activity and receipt; no additional source facts, counts, or matches |
| No external ID, same hash | Exact duplicate; same activity |
| Official delivery hash matches earlier manual import | Bind verified provider alias to the same activity if ownership/identity are coherent; no second run |
| Same external ID, different hash | Stage immutable source revision and require owner review; keep prior accepted facts until explicit audited acceptance |
| Different external IDs, same hash | Same recording candidate with additional verified aliases; preserve provenance, require review if account/identity conflict exists |
| External reference resolves to activity A, hash resolves to B | Identity conflict; do not silently coalesce two histories |
| Similar totals/time but different bytes and no verified external ID | Possible-duplicate notice only; owner decides, no fuzzy auto-dedupe |
| Reimport of an owner-removed activity | Preserve removal/tombstone; offer explicit restore, never resurrect via background delivery |

If an accepted source revision changes facts used by a confirmed match, retain the payload reference used by that match and request explicit rebind/correction. A new transport payload cannot silently change which historical evidence completed a planned workout.

## Manual original FIT pipeline

1. Owner chooses Import original FIT from contextual Garmin settings/import screen. Garmin's support page documents Export Original through the website; show concise assistance without collecting a Garmin password. Files usually are FIT, not universally so. [G4]
2. Pick one file through the existing File API; read at most the configured byte limit plus a sentinel byte. Treat MIME/extension/declared size as hints and enforce actual read bounds. Keep content URI and filename inside the adapter. Cancellation produces no error and no source writes.
3. Calculate SHA-256 on the exact selected bytes. Validate FIT header/length/CRC with the official SDK integrity API. Do not set `skipHeader`/`dataOnly` to recover arbitrary corrupt input. A successful CRC is format integrity, not proof of trusted origin. [F1]
4. Decode using ArrayBuffer/typed arrays, not Node `fs` or Buffer-only entry points. Set options explicitly and reject parse errors under the strict import policy. Version parser behavior, including enum/array representation and HR merging. Preserve partial-field absence; do not import decoder-produced zeros as fabricated measurements. [F1]
5. Validate exactly supported running session structure. Preserve the distinction between outdoor, treadmill, indoor/unknown, and unsupported/multisport data. v1.2 should reject unsupported multisport imports with a useful reason instead of silently discarding sessions. Do not infer treadmill solely from missing GPS.
6. Normalize to a pure immutable draft. Bound bytes, decoded message count, lap count, sample count, nesting, duration, and output bytes; malformed payloads cannot exhaust UI memory. Choose explicit numeric limits from representative owner fixtures and native memory measurements before shipping. No unmeasured upper bounds are claimed here.
7. Resolve duplicate/revision/conflict status. For a valid new activity, the owner's file selection authorizes import: commit, then open the factual detail preview with missing-field states, matching the prototype without adding an extra confirmation modal. Conflicting identities, changed accepted source revisions, and ambiguous historical dates need explicit review. When committing, recheck identities and expected aggregate revision inside one exclusive transaction, write all source rows and the receipt, then publish success and invalidate projections. Two simultaneous manual/API imports must settle through constraints and receipt replay.
8. Cleanup temporary bytes/files on cancellation, validation failure, committed success, and startup after interruption. Import must not suspend or mutate a live strength session. If decoder work cannot meet the existing JS responsiveness budget, defer import while working out or move parsing behind a measured background/native adapter; do not run it inside Reanimated's UI runtime.

The prototype's file-input handler picks a canned activity and simulated receipt. That behavior provides presentation/state guidance only. Real format parsing, mutation acknowledgment, error recovery, and dedupe use this domain contract.

## Field interpretation and presentation

| Source fact | Store | Display / guard |
|---|---|---|
| Session start and elapsed duration | UTC instant, explicit available offset/local-time provenance, elapsed seconds | Historical date must not move when the phone changes time zone. If source offset is absent, use an explicit proposed zone for owner confirmation and persist it |
| Timer-running duration | Separate seconds field | Do not label it Moving without verified moving-time provenance. “Elapsed,” “Timer,” and “Moving” are distinct concepts |
| Distance / speed | Metres, metres per second, source-present flags | Average pace computed from the documented chosen time basis and positive distance; no pace for missing/zero distance. Preserve basis in evidence |
| Session / lap summaries | Original summary values and original order/index | Lap columns stay **Lap, Time, Pace**. Prefer lap timer time for Lap Time under a documented convention; surface missing lap time/distance honestly |
| Laps | Session association and stable source index | Do not assume array order alone across multisport sessions. Missing laps do not become invented 1 km splits [F2] |
| Record positions | Valid coordinates converted per FIT profile into decimal degrees with timestamps and segment breaks | Outdoor route optional; invalid sentinel values rejected before conversion. Break across missing segments and improbable jumps; never connect an entire route through (0,0) as a placeholder |
| Heart rate | Source summary where present; valid samples and gaps | Average HR shown only when supported; absent HR is not zero. Preserve difference between imported summary and any derived estimate |
| Treadmill subtype | Explicit supported source subtype plus evidence | Always show **No route for treadmill activity**; keep available distance/time/pace/laps and optional HR |
| Outdoor without coordinates | Kind plus `routeAvailability=missing` | No fake map or treadmill reclassification; other facts remain accessible |
| Sparse / missing metrics | Nullable values and capability flags | No target/readiness/fitness score fabricated from an incomplete import |

Static route rendering uses aspect-preserving projection and gap segments from the actual source coordinates, not an invented road network. Dateline/extreme-coordinate cases need explicit handling. Downsample only a rebuildable display projection, with a measured point cap; source sample chunks remain lossless. Accessible text/data alternatives accompany charts. Rendering existing data requires no live location permission or background tracking.

## Owner-confirmed schedule matching

This section coordinates with the domain researcher's proposed `plans.plan_kind`, `running_plan_profiles`, `running_plan_day_revisions`, and existing `owned_plan_schedule_opportunities` / schedule versions.

1. Candidate selection is a read query, scoped to Running plans and real materialized opportunities. Rank by date/time/session type as assistance; no candidate automatically completes anything. Multiple ordered session slots on the same date remain separate candidates with stable identities. Unmatched imports remain visible in Calendar/Progress and do not create or activate a plan.
2. The confirmation sheet identifies activity/date, selected plan/day/opportunity, and relevant schedule/running revision. Same-day concurrent plans remain distinguishable. The selected opportunity is a stable ID, not “the active plan” or a date-only key.
3. Confirm command carries request ID, imported activity + accepted payload revision, opportunity ID, schedule version, plan-day ID, running-day revision, and expected current relation state.
4. Exclusive transaction rechecks owner identity, source visibility, payload revision, opportunity eligibility, conflicts/skip/override state, and current schedule view. Write the immutable match event, rebuild/update the completion overlay, and commit the receipt atomically. A stale sheet is rejected for fresh review.
5. The shared effective schedule resolver treats the overlay as completion. Skip/missed/override commands query the same overlay in their own transaction. Avoid separate competing definitions of completion.
6. Calendar emits one activity fact with its planned linkage, not both an imported run and a synthetic completed planned run. Progress counts each accepted source activity once; unmatched activities can contribute factual Running history without implying plan adherence.
7. Unmatch/reassign needs an explicit owner command and new event; never delete old events. Each command checks both old and new relations and invalidates affected projections. Removing an activity invalidates its current match through an audited operation. No delayed delivery reinstates a removed/unmatched relation.

For the initial Running weekly schedule proposal, use Weekday scheduling. Avoid introducing retroactive Running rotation consumption/reversal semantics as a side effect of import. Strength's existing rotation remains governed by the domain migration. Calendar date corrections change owner overlays explicitly, not source FIT timestamps.

### Proposed broker boundary

The phone opens browser consent with state and S256 PKCE. A reviewed broker performs any exchange requiring the shared secret and stores provider refresh credentials server-side by default. The phone receives only an app-scoped session/opaque completion result through an authenticated, one-time handoff; avoid tokens in redirect URLs. Exact callback/handoff topology must match the approved Garmin client contract and existing Android link scheme/signature configuration. No custom auth endpoint paths are specified in this research.

The broker owns inbound internet callbacks and fetches only approved provider origins. It maintains bounded event dedupe and delivery checkpoints. The phone imports verified activity bytes through `GarminActivitySourcePort`. Callback payloads are untrusted hints until authenticated/reconciled against the approved contract. HTTP success is acknowledged after durable receipt, then parsed/imported work can retry. Acknowledgment timing/retry codes must follow partner documentation, not guessed webhook conventions.

Disconnect increments connection generation before stopping pending work and clearing local app credentials. A late callback/download from a prior connection cannot write into a newly connected account. Retaining already imported owner history versus deleting it is a separate explicit action; current partner terms may impose additional deletion requirements, which must be resolved before activation. Restore/merge cannot resurrect an authorized connection.

## Backup, recovery and privacy

1. Add the import/source/match aggregates explicitly to a versioned logical portability contract (proposed v3); preserve reading existing v1/v2 archives. Do not simply append mandatory new tables to a historical version's required table set. Export source facts; exclude token/cursor/job caches and rebuild completion/chart/calendar projections after restore.
2. Use lossless bounded sample chunks. A proposed maximum raw chunk size of 32 KiB leaves headroom under the existing 64 KiB string bound if base64 representation is selected. This is a storage recommendation to validate, not a claim that chunking fixes the total archive cap. Specify/check encoding, channel schema, counts, monotonic deltas, expanded size, checksums, and units.
3. Capacity preflight estimates resulting total source snapshot size/rows before accepting an import. A full backup capacity must not become a later surprise after an activity was accepted. If history needs larger limits, review a streaming/chunked archive extension and native memory evidence; do not bypass current resource bounds or silently omit imported history.
4. Candidate restore uses the existing isolated validation/reconciliation path. Remap `(owner_namespace, portable_id)` aggregates and child keys before publishing; never join two owners merely because Garmin IDs or hashes coincide. Same-owner duplicate payloads become no-ops; conflicting accepted revisions/removals/matches require preview and owner resolution.
5. Rebuild `running_opportunity_completions` from valid immutable events after restore/merge. An opportunity deleted or changed by reconciliation cannot acquire completion through a dangling local ID. Provider external refs remain provenance only and never reauthenticate anything.
6. Keep routes and HR out of diagnostic payloads, test screenshots committed as fixtures, and generic error text. Use synthetic/public-license fixtures or explicitly approved private fixtures; do not print owner activity files or account subjects. Counts, classified error codes and opaque receipt IDs are sufficient diagnostics.
7. Extend Android cloud-backup **and** device-transfer exclusions for Garmin temporary storage and device credentials. With custom backup rules, reconcile SecureStore configuration explicitly. Verify generated manifest/XML later; no native files are generated in this planning session.
8. Existing archive encryption protects exported backups. It does not prove live SQLite is encrypted at rest. This design does not silently claim database encryption; any stronger route/health at-rest requirement is a separate owner/security decision.
