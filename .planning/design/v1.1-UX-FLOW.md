# v1.1 UX Flow — Active Workout Overview & In-Workout Exercise Editing

**Status:** DRAFT for owner review. Nothing here is built or planned yet. This doc exists so you can approve the interaction model before GSD planning starts.

**References:** Hevy (16M+ users; empty-workout build-as-you-go, per-exercise rest timer, supersets, mark set complete → auto rest), Strong ("clear winner… easy to use even mid-workout", supersets, custom timers). Both use a **single scrollable session sheet**, not a one-exercise-at-a-time wizard.

---

## 1. The core question you asked: overview list vs. jump into first set

### What we do today (v1.0)
Starting a workout routes straight into `ActiveWorkoutScreen`, which is effectively **one exercise in focus** (`currentExercise`) with its warm-ups and working sets and an inline Complete action. To reach another exercise you rely on the sticky identity / plan review, not a top-level list.

### What Hevy / Strong do (the industry norm)
The active workout is **one vertical scrollable page**: every exercise is a card/section header with its set rows beneath it, in order, top to bottom. You:
- see the whole session at a glance (what's done, what's left),
- tap the checkmark on any set to complete it and auto-start that exercise's rest timer,
- scroll to any exercise at any time (no forced sequence),
- have a persistent **"+ Add exercise"** button pinned at the bottom of the list,
- open a per-exercise **overflow menu (⋯)** for Replace / Remove / Reorder / notes / rest-timer / superset.

Neither app forces you into "set 1 of exercise 1." The overview *is* the workout screen.

### Recommendation: **YES — reorient to a session overview (WORK-19).**

Rationale specific to this app:
- It's the natural home for add/replace/remove/reorder — those actions are meaningless without a list to act on. Building the overview first makes the rest of v1.1 coherent.
- Your v1.0 model already computes `view.exercises[]` (the whole session) and per-exercise `status: planned | active | completed | skipped`. The overview is largely a **presentation** of data the domain already exposes — lower risk than it sounds.
- It preserves the one-tap loop: Complete stays inline on each set row; the active set is the default scroll anchor so a returning/mid-set user isn't hunting.

**Nuance worth deciding (see Open Questions Q1):** "active set anchored on entry" keeps the fast path for someone mid-exercise, while still showing the list. Pure Hevy shows top-of-list; I lean toward *anchor to active set but render the full list above/below* so both the overview and the one-tap flow win.

│     Set 3       80kg × 5                     │
│     + Add set                                │
│                                              │
│  ▸ Bench Press                           ⋯   │
│     Set 1       60kg × 8                      │
│     + Add set                                │
│  … (scrolls) …                               │
│                                              │
│  ┌───────────────────────────────────────┐  │

- **Sticky header** keeps the existing workout identity plus a **session overflow (⋯)** for whole-session actions (Finish, discard, etc. — already in the More sheet today) and — new — "Reorder exercises."

- **Add set** stays where it is today (per-exercise), unchanged.
- **Add exercise** is a new pinned button at the list end.
- **RestDock** is unchanged from v1.0.

## 3. Flow: Add exercise (WORK-20)

1. Tap **+ Add exercise** → opens the reviewed library picker (same shared Material 3 Search/filter used in plan editing and Progress).
2. Select one exercise (v1.1 scope = single; multi-select is an open question, Q4).
3. It appends to the **end** of the session as a new exercise section with:
   - its metric profile's default target scheme,
   - one empty working set ready to fill,
   - an `added` badge (distinct from planned exercises),
   - a fresh immutable snapshot (WORK-24).
4. The list scrolls to the new exercise; nothing else changes.

**History/data:** append-only. No planned exercise is touched. The added exercise has null plan-target lineage → manual targets, no auto-progression (consistent with v1.0 "no snapshot → manual").

---

## 4. Flow: Replace exercise (WORK-21)

Exercise header **⋯ → Replace**. Two cases, decided by whether it has completed working sets:

- **No completed sets yet:** the exercise is removed and the chosen replacement is appended **in the same display position**. Clean swap.
- **Has ≥1 completed set:** the original is **kept and marked skipped** (its completed history is preserved and visible in history), and the replacement is appended in its position. We never rewrite the original's rows.

Either way the replacement is picked from the library and carries its own snapshot. This mirrors v1.0's existing plan-level `replaceExercise` (fresh identity, never mutate).

---

## 5. Flow: Remove exercise (WORK-22)

Exercise header **⋯ → Remove**.

- **No completed sets:** hard-delete the whole exercise from the session (analogous to today's non-completed set removal).
- **Has ≥1 completed set:** cannot hard-delete; instead **skip** it — completed history stays, and it's excluded from remaining-work counts. UI copy makes this explicit (e.g. "This exercise has completed sets and will be marked skipped, not deleted").

Progress totals and history snapshots stay correct and rebuildable after either outcome.

---

## 6. Flow: Reorder exercises (WORK-23)

- Enter reorder via session **⋯ → Reorder exercises** (or long-press an exercise header).
- Touch-and-hold drag to reposition; accessible up/down buttons as fallback (reuses the drag-first pattern shipped in v1.0 Phase 7 plan editing).
- Reordering changes a **display order only**. The planned order captured at session start stays immutable for history. Completed-set facts are untouched.

## 7. What stays exactly as v1.0 (no change)

- Inline set Complete/Skip/Retry, eight-second Undo, rest timing + RestDock, notification reconciliation, process-death recovery.
- Per-exercise Add set / Remove set (non-completed only) and completed-set correction.
- The immutable-snapshot guarantee (WORK-24 only clarifies and extends it; it does not relax it).

## 8. Advanced timing (WORK-26) and Cross-device history / Merge restore (DATA-08/09)

- **WORK-26 (per-rep / cluster timers):** **both modes ship in v1.1** (owner decision Q10). Configured per exercise/set via the exercise overflow or set editor; emits advisory cues only (per-rep cadence beep; cluster intra-set rests, e.g. 3+3+3, recorded as one set). It's a Phase 10 concern and does not alter the overview layout beyond a small timer indicator. Detailed UX specced in its own phase.
- **DATA-08 / DATA-09 / DATA-10 (portable history + automatic Google-Drive sync):** lives in Settings → Data & recovery. The owner keeps **one canonical, encrypted store**. Three layers:
  - **Restore-clean** (today's path) and **merge-into-existing** (DATA-08, new, with a preview + per-record conflict rules) — the manual import/export fallback (DATA-09).
  - **Automatic sync (DATA-10):** the owner optionally signs into Google (One-Tap, `drive.file`); the app then keeps an app-created **encrypted** Drive file in sync automatically — reconciling on app foreground, on background/close, and after a workout/edit commits. Google sees only ciphertext. Sign-in is optional and reversible ("Disconnect sync"); the app logs workouts fully offline without it.
  - Phases 11 (portable/merge) and 12 (auto-sync); neither changes the active-workout overview UX beyond a small sync-status indicator in Settings/Today.

### Sync UX (DATA-10) — Settings → Data & recovery

```
Data & recovery
  Cross-device sync
    ○ Not connected                          [ Connect Google Drive ]
    ● Synced · last synced 2m ago · <account> [ Sync now ] [ Disconnect ]
    ⚠ Sync paused (offline / auth expired)    [ Retry ]
  Backup & restore (manual)
    [ Export backup ]  [ Import / merge backup … ]
```

- **Connect Google Drive** → One-Tap sign-in → grant `drive.file` → first sync uploads the encrypted store (or merges if the Drive file already exists from another device).
- Sync is **silent and automatic** thereafter; the status line is the only surface. No blocking spinners on the workout path.
- Conflicts are resolved by the DATA-08 engine (newest-wins for sessions/corrections, existing-wins for settings, keep-both for distinct custom exercises/plans) — never a blind overwrite; local SQLite stays authoritative.

## 8a. Flow: End-of-workout "Save changes to plan?" (WORK-27)

When a workout that was **edited mid-session** (added/replaced/removed/reordered exercises) reaches the finish/completion flow:

1. After the normal completion summary, show one explicit choice:
   > *"You changed this workout from its plan. Save these changes to [Plan · Day A]?"*
   > **[ Keep plan as-is ]** (default, focused)  **[ Save changes to plan ]**
2. **Default is No** ("Keep plan as-is"): all edits stay session-scoped; the plan is untouched; recorded history is untouched.
3. **Save changes to plan:** applies the session's add/replace/remove/reorder deltas to the owning plan day through the existing v1.0 owned-plan editing path (revision-checked, atomic, no silent mutation). Already-recorded set history is never altered.
4. The prompt appears **only** when the session actually diverged from its planned day; it never appears for empty/unplanned workouts or unedited sessions.

This keeps plan editing an explicit owner action (consistent with v1.0) while giving you the one-tap "yes, make it permanent" path at the natural moment.

## 9. Summary of the decision you're approving

1. **Reorient the active workout to a scrollable session overview** (all exercises + sets), anchored to the active set on entry, Complete still one tap. ← the main UX change.
2. Add/Replace/Remove exercises via a per-exercise overflow; Add exercise via a pinned button; Reorder via drag.
3. All of it is **append-only over immutable snapshots**; completed history is never destroyed (replace/remove degrade to skip when completed sets exist).
